## 結論

この4つの言葉は、**別々の2つの軸**で考えると一気にクリアになる。

| 軸 | 言葉 | 意味 |
| --- | --- | --- |
| **何を担当するか**（関心領域・職種） | フロントエンド / バックエンド | 開発の役割・領域の分け方 |
| **コードがどこで実行されるか**（実行場所） | クライアントサイド / サーバーサイド | プログラムが動く場所の分け方 |

おおまかに「**フロント ≒ クライアント**」「**バック ≒ サーバー**」と対応するが、
**完全なイコールではない**。ここを分けて考えるのが理解の核心。

## 詳しく

### 軸①：フロントエンド / バックエンド（＝担当領域）

- **フロントエンド**：ユーザーが直接触れる **見た目・操作（UI/UX）** をつくる領域。
  HTML / CSS / JavaScript、React・Vue などのフレームワーク。
- **バックエンド**：表からは見えない **サーバー側のロジック・データ処理** をつくる領域。
  API、認証、ビジネスロジック、データベース操作など。言語は Node.js / Go / Python / Ruby / Java など。

これは「**人の役割・関心**」の分類。求人の職種区分もこの軸。

### 軸②：クライアントサイド / サーバーサイド（＝実行場所）

- **クライアントサイド**：**ユーザーのデバイス**（ブラウザやスマホアプリ）の上で実行される処理。
  例：ボタンを押したときの画面の動き、フォームの入力チェック（ブラウザ上の JS）。
- **サーバーサイド**：**サーバー（遠隔のコンピュータ）** の上で実行される処理。
  例：ログイン認証、DBへの保存、決済処理。

これは「**コードが物理的にどこで動くか**」の分類。

### なぜ混同するのか

通常はこう対応するため、ほぼ同義に語られる：

```
フロントエンド  ──主に──>  クライアントサイドで実行
バックエンド    ──主に──>  サーバーサイドで実行
```

しかし**ズレる例**があるので「≒」であって「＝」ではない：

- **SSR（サーバーサイドレンダリング）**：Next.js などで画面（フロントエンドの成果物）を
  **サーバーサイドで**生成して返す。→ *フロントエンドの仕事だが実行はサーバー側*。
- **Node.js**：もともとブラウザ用言語だった JavaScript を **サーバーサイドで**動かす。
  → *フロントの言語がサーバーで動く*。
- **入力バリデーション**：使い勝手のためクライアントサイドで、改ざん対策のため
  サーバーサイドでも、と**両方で**実装するのが定石。

### ざっくり対応イメージ

```
[ユーザーのブラウザ]            [サーバー]
 └ クライアントサイド            └ サーバーサイド
   ・画面描画/操作                ・API/認証/DB
   ・主にフロントエンド担当        ・主にバックエンド担当
        ▲                              ▲
        └──── HTTP リクエスト/レスポンス ────┘
```

## まとめの一言

- **フロント/バック** ＝ 「**担当（だれが何をつくるか）**」
- **クライアント/サーバー** ＝ 「**場所（どこで動くか）**」
- 多くは対応するが、SSR や Node.js のように**交差するケースがある**と知っておけば迷わない。
